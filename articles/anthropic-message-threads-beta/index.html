Anthropic 给长会话智能体减负：消息线程公测，首字延迟降约 35%

Anthropic 官方文章宣布消息线程公开测试：长会话每轮只发新增消息，50 万到 100 万 token 请求的首字延迟中位数降约 35%，token 用量与计费不变。

KEY TAKEAWAYS / 要点

  • 02THE CONFIRMATION：Unite.AI 等独立报道核对机制与数字，与官方口径一致。
  • 03THE WATCHPOINT：测试期限制何时放宽，线程是否走向可检索与持久化。

WHAT HAPPENED发生了什么

Anthropic 官方文章称，消息线程已在 Claude 平台进入公开测试：智能体只需在首个请求里发送完整对话，此后每轮只发新增消息与上一条回复的编号，服务器在轮次之间代为持有对话。

官方给出的收益数字来自 Claude Code 的默认开启推广：在 50 万到 100 万 token 的请求上，首字延迟中位数下降约 35%。多家独立报道转述的请求体积变化是，典型长对话的单次请求从约 800KB 降到 1.8KB。

机制有明确边界：线程只存在内存里、加密且不落盘，距离上次请求 5 分钟后过期，过期后客户端要重发完整对话开新线程；Claude 每轮仍读完整对话，因此 token 用量、计费与速率限制不变。

可用范围覆盖原生 Claude 平台、AWS 上的 Claude 平台、Microsoft Foundry 中的 Claude，以及 Anthropic 管理的 Google Cloud 上的 Claude 模型，按标准 token 价格与现有速率限制计费。

官方同时列出测试期限制：线程尽力而为、没有列出、读取或删除线程的接口，不支持消息批次、token 计数与多数上下文编辑，零数据保留与 HIPAA 机构不在适用范围。

WHY IT MATTERS省的是延迟，不是 token 账单

消息线程解决的是长会话里最烦人的部分：每轮重传几十万 token 的对话，模型还没开口就先花掉时间。只发新增内容，首字来得更快，但模型照单全读，账单原封不动。

对开发者而言，这是一个纯延迟优化，不是成本优化。把线程当成缓存来用是对的，把它当成对话存储是错的，应用仍需自己保存完整记录并留好全量重发路径。

WHY IT MATTERS长会话智能体的基础设施正在补齐

编程智能体一轮会话能发几百次请求，截图与工具结果越积越长，重传成本随会话线性膨胀。消息线程这类机制出现，说明长会话已经从演示变成日常负载，平台开始为它修基础设施。

下一信号是测试期限制何时放宽：线程可检索、可持久化、支持零数据保留的那一天，长会话智能体的部署形态会再变一次。

SIGNAL JUDGMENT延迟优化，不是成本优化

Tokenta Signal 判断：消息线程的价值在长会话的响应速度，不在账单。把它当缓存用，自己的对话记录仍要握在手里。

本篇事实以 Anthropic 官方文章为准，延迟与请求体积数字为官方在 Claude Code 内部推广中的自报数据，未经独立测试。本文只做摘要与链接，不转载原文全文。本文不构成任何投资建议。
